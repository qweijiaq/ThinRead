# AI 任务的状态，不能只存在前端

做 AI 功能，很容易把“任务”当成一个 Promise：点击按钮，显示 loading，等结果回来，结束。

短请求这样没问题。一旦任务变成整本书生成、整份文档翻译、几十页 PDF 的 OCR，它就可能跑十几分钟。用户会切窗口、会刷新页面、会关掉应用，甚至会因为网络抖动重试。这个时候，前端的一个 `loading` 状态就不够用了。

以下内容来自一个读书工具项目的实践。项目里有整本生成、整本排版、整本翻译和扫描版 PDF 的 OCR，都是长任务。最初这些任务的状态只放在 React 里，后来慢慢搬到了 SQLite。

## 一、用户关掉窗口之后

最早的状态大概是这样的：

```ts
const [running, setRunning] = useState(false)
const [progress, setProgress] = useState(0)
```

点击按钮，`running` 变成 true，主进程通过事件把进度发回来。窗口一刷新，`running` 和 `progress` 都回到初始值；如果主进程还在跑，用户看不到；如果主进程也退出了，下一次打开应用，就像什么都没发生。

更麻烦的是“部分完成”。整本生成跑了 18/30 章，进程退出了。用户回来看到书架没有变化，不知道是该重新点一次，还是等一等。重新点一次，前 18 章可能又跑一遍，钱也再花一遍。

问题不在于进度条做得不好看，而在于状态只存在一个会消失的地方。

这里说的“任务”，不只是整本书。批量翻译、批量导出、批量识别、批量打标签，只要它由多个子步骤组成、耗时超过几十秒，就会遇到同样的问题。任务越贵，用户越不希望它从头再来。

## 二、把任务写进数据库

长任务需要一张表。表里不需要存正文，也不需要存 prompt，只需要记住“要处理谁”和“做到哪了”。

```sql
CREATE TABLE background_tasks (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,
  book_id TEXT NOT NULL,
  payload TEXT NOT NULL,
  status TEXT NOT NULL,
  done INTEGER NOT NULL DEFAULT 0,
  total INTEGER NOT NULL DEFAULT 0,
  failures TEXT NOT NULL DEFAULT '[]',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

`payload` 里存任务目标：要做哪些章节、每章标题是什么，以及少量选项。正文在数据库里，任务只需要记住目标 id。

不要把正文或 prompt 塞进任务表。它们会让表迅速变大，也会让“删除一本书”变成一件很麻烦的事。任务表的价值是索引，不是内容仓库。

任务 id 也要稳定。比如 `notes:<bookId>`、`translate:<bookId>`、`ocr:<fileId>`。稳定 id 让同一个任务可以被更新、查询和去重，而不是每次点击都生成一条新记录。

状态可以只有几种：`running`、`paused`、`done`、`error`、`cancelled`。`paused` 是专门为“应用重启”准备的。

## 三、启动时，把 running 改成 paused

主进程启动时，做一件事：

```ts
export function markInterruptedBackgroundTasksPaused(): void {
  getDatabase()
    .prepare("UPDATE background_tasks SET status = 'paused' WHERE status = 'running'")
    .run()
}
```

上一次进程退出时还在跑的任务，一律标成暂停。不是失败，也不是完成，而是“需要用户决定要不要继续”。

这个区分很重要。失败意味着“这次没成”，暂停意味着“还可以接着来”。界面上会显示“应用重启，任务已暂停；继续会跳过已完成章节”，而不是一个红色的错误。

状态变化最好集中在一个地方。`running` 只能从“用户点击继续”进入，`done` 只能在所有目标都有结果后进入，`error` 要带失败列表。不要让 UI 直接改数据库里的状态字符串，否则很容易出现“界面显示完成、数据库还是 running”的分裂。

如果有多个窗口，任务状态还要考虑并发。一个窗口点了继续，另一个窗口不应该再启动同一份任务。用任务 id 做互斥，比在 UI 上禁用按钮更可靠。

## 四、继续时，只做没做完的

任务里记录了每个目标的 id。继续时，代码先查这些章节是不是已经有结果：

- 整本生成：已经有非空读薄稿的章节，跳过；
- 整本排版：已经有排版结果的章节，跳过；
- 整本翻译：已经有结构化译文的章节，跳过；
- 成稿：没有“部分完成”的概念，只能重新生成。

所以“继续”不是从头再来，而是从任务记录里剩下的目标开始。失败章节也会记录 chapterId 和错误信息，任务中心可以只重试失败的那几节，不用整本重跑。

判断“已经有结果”不能只看任务表，要看真正的结果表。比如生成任务要检查该章节是否已经有非空读薄稿，翻译任务要检查是否已经有结构化译文。只看任务状态，可能会把“上次标记完成但实际没写入”的章节跳过。

这也意味着任务执行要尽量幂等：同一章重复处理一次，不应该产生两份笔记、两条翻译。写入时用章节 id 做唯一约束或覆盖写入，比事后去重更省事。

这里有个细节：任务记录是主进程写的，但进度事件是发给渲染进程的。如果渲染进程刷新了，内存里的任务列表会丢，但数据库里的记录还在。重新加载时，界面从 `tasks:list` 恢复，不依赖之前那一路事件。

这也是后来才想明白的：进度不能只存在 UI 里。UI 可以丢，数据库不能。

## 五、实时进度和持久化记录要分开

短任务用 Toast 就够了，比如“已复制”“已保存”。

长任务需要任务中心：能看到进度、失败原因、继续按钮，还能在切换页面后回来。任务中心的数据来自两处：

- 主进程发来的实时进度；
- 数据库里的持久化记录。

实时进度让数字动起来，持久化记录保证刷新后还在。两者合并时，以数据库记录为底，实时事件只更新状态和进度。

不要把实时事件当成唯一数据源。事件会丢，页面会刷新，任务却还在跑。

事件也不需要全部重放。界面重新挂载时，先从数据库拿一份快照，再订阅后续事件就够了。事件里带的进度可以用来更新数字，但不要用它来推断任务是否存在。

任务中心还应该能区分“正在跑”和“刚跑完”。用户切回来时，看到“已完成 30/30”比看到一个停住的进度条更安心。完成状态最好保留一段时间，而不是立刻从列表里消失。

## 六、通知和状态是两件事

用户把窗口切到后台，任务还在主进程里跑。完成时如果窗口不在前台，可以发一条桌面通知。

```ts
new Notification({ title, body }).show()
```

不是所有任务都发。只有窗口失去焦点时才发，避免用户盯着进度条时被重复打扰。整本生成、整本排版、整本翻译完成或失败时会发；单章生成一般很快，不发。

通知内容也应该克制：完成了、失败了、有几节失败。不要把正文或笔记标题塞进去，避免在锁屏或通知中心泄露阅读内容。

通知只是提醒，不承担状态恢复。用户点开应用后，仍然应该从数据库里看到任务的真实状态。

通知的点击行为也要想清楚。点击后是打开任务中心，还是直接打开结果页？如果任务已经失败，打开一个空白结果页只会让人困惑。通知里可以只写“整本生成完成”或“有 3 节失败”，具体内容留给应用内展示。

## 七、OCR 和批处理也是同一类问题

扫描版 PDF 的 OCR 是另一条长任务线。它有自己的 job 表，记录页码、状态和输出文件。

应用启动时，会把上次还在 `running` 的 OCR job 标成中断，界面上显示“上次 OCR 未完成，继续”。继续时从上次的页码接着做，不重新识别前面的页。

批处理、批量导出、批量打标签，本质上都是同一个问题：任务可能在中途被打断，用户需要一个地方看到“还剩什么”，而不是只有一个“重新开始”。

取消也要认真处理。取消不是把 UI 关掉，而是要让后续的请求不再发出，正在跑的请求收到中止信号，已经完成的部分保留下来。取消后任务状态应该是 `cancelled`，而不是 `error`。

如果一个任务已经完成了一半，取消后再次开始，应该问用户是“继续剩下的”还是“全部重来”。这两个选项的成本差别很大，不要让用户猜。

## 八、任务中心应该回答三个问题

用户打开任务中心，通常只想知道三件事：

1. 现在做到哪了？
2. 有没有失败？
3. 我能不能继续？

所以任务中心不需要展示所有内部步骤。一个进度条、一句状态、一个失败数量、一个继续按钮，基本就够了。更细的日志可以放在详情里，不要占主界面。

失败列表要能定位到具体章节或文件，并且支持单条重试。只显示“任务失败”而没有原因，用户只能整本重跑。

完成后的任务也不要立刻消失。保留最近几条完成记录，用户才能确认“刚才那次确实跑完了”。可以设置一个保留期限，比如七天。

## 九、上线前可以逐条检查

- 任务状态是否持久化，而不是只放在组件 state 里？
- 应用重启后，进行中的任务会变成什么状态？
- 用户能否只重试失败的子任务？
- 已完成的部分是否会被跳过？
- 实时进度丢失后，界面能否从数据库恢复？
- 通知是否只在窗口不在前台时发送？
- 通知内容是否避免了敏感信息？
- 取消操作是否能真正停止后续请求？

长任务做起来不复杂，难的是把它当成一个会在任意时刻被打断的系统来设计。

一个任务能跑完，当然好。但如果它在中途被打断，用户回来还能看到“做到哪了、还剩什么、要不要继续”，这才算可靠。

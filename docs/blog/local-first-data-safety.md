# 本地优先，真正的难点是“怎么不丢数据”

做本地优先的应用，很容易被“数据都在你自己的电脑上”这句话安慰到。

不用服务器，不用账号，不用同步，听起来少了很多麻烦。但本地也有本地的问题：硬盘会坏，进程会崩，用户会手滑删库，升级也可能把表结构改坏。云端产品可以把这些问题推给服务端，本地应用不行，得自己把“后悔药”做出来。

以下内容来自一个本地读书工具的实践。它用 SQLite 存书籍、章节和笔记，书文件放在数据目录里。下面这些兜底不是一开始就有的，很多是在测试和真实使用里慢慢补上的。

## 一、数据库升级：只许往前走

SQLite 自带一个 `user_version`，可以用来记录 schema 版本。每次结构变化，追加一条迁移，而不是回头改上一条。

```ts
export const SCHEMA_VERSION = 7

const MIGRATIONS = [
  { version: 1, run(conn) { /* ... */ } },
  { version: 2, run(conn) { /* ... */ } },
  // ...
]
```

这样做的好处是可预测：用户从任意旧版本升上来，都是按顺序补齐。测试里可以造一个 `user_version = 0` 或 `3` 的旧库，跑一遍迁移，确认最后版本等于 `SCHEMA_VERSION`。

坏处是迁移只能加，不能删。旧代码留下的字段、索引、空表会一直存在。这个代价可以接受，因为“升级到一半失败”比“多一个字段”严重得多。

迁移本身也要尽量幂等。比如加字段前先查 `PRAGMA table_info`，避免重复执行时报错。早期没这么做，测试里重建数据库时就吃过亏。

迁移要放在事务里。一个版本里有多条 `ALTER TABLE`，如果执行到一半失败，最好整体回滚，而不是留下一个“改了一半”的库。SQLite 的 DDL 支持事务，这一点很有用。

升级前也应该有一份自动备份。用户不一定手动备份，但版本升级是少数可以提前预料的破坏性操作。备份失败时，是继续升级还是停下来提示用户，要有一个明确策略。

迁移失败后，不要反复重试同一条半执行的迁移。先把数据库恢复到升级前，再让用户重试，或者提示用户导出数据。最糟糕的情况是应用每次启动都卡在同一条迁移上。

## 二、删除不是删除，是先搬家

删除一本书，最早是直接 `DELETE FROM books`，再把书文件目录 `rm -rf`。逻辑很干净，直到有人问：删错了怎么办？

后来改成了书籍回收站：

- 删除前把书、章节、笔记的完整行序列化成 JSON，写进 `book_trash`；
- 书文件目录从 `books/<id>` 移到 `trash/books/<id>`；
- 数据库行删除，但回收站记录保留 30 天；
- 恢复时把 JSON 里的行插回去，再把文件移回来；
- 彻底删除和清空回收站才真正删文件。

这里有一个容易忽略的点：移动文件可能失败，数据库写入也可能失败。如果文件已经移走、数据库写入失败，用户会看到书没了，但回收站里也没有。所以代码里做了补偿：数据库写失败时，把文件移回原位。

30 天这个数字不是法律要求，也不是备份策略，只是一个产品选择。太短，用户来不及发现；太长，磁盘占用又下不去。到期后启动时清理，删除 `book_trash` 记录和对应的文件目录。

软删除和回收站不是一回事。软删除通常只是在行上打一个 `deleted_at`，查询时过滤掉；回收站则可能把数据移到另一张表，甚至把文件移到另一个目录。前者实现简单，后者更容易做“彻底删除”和容量统计。选哪种，要看数据量和恢复流程。

移动文件时还要考虑跨设备。`rename` 在同一个文件系统里通常是原子的，但跨磁盘可能失败。失败时不能把数据库行也删掉，否则文件还在、索引没了。比较稳的顺序是：先保存可恢复的数据，再移动文件，最后删除原记录；任何一步失败都能回退。

恢复时也可能遇到冲突：回收站里的书和书架里现有的书 id 相同。恢复前要检查，不要直接覆盖。可以提示用户“这本书已经存在”，或者生成一个新的 id。

## 三、备份不是复制一个数据库文件

最早的备份就是复制 `reading-notes.db`。后来发现两个问题：

第一，SQLite 可能还有 WAL 和 SHM 文件，直接复制主库不一定是一致快照；
第二，书文件在 `books/` 目录里，只备份数据库，恢复后书还在，但封面和原文件没了。

更稳的备份流程是：

1. 用 SQLite 的备份接口生成一个临时数据库快照；
2. 把 `books/` 下的文件按内容哈希存进 blob 存储；
3. 生成 manifest，记录每个文件对应的哈希和大小；
4. 把数据库、设置、manifest 打进压缩包；
5. 写入元数据，记录备份 id、时间、类型和引用到的哈希。

文件按内容哈希存储，多个备份引用同一份文件时不会重复占空间。清理备份时，再根据 manifest 回收没有被任何备份引用的 blob。

这部分代码不复杂，但很容易漏掉“备份失败后的清理”。比如压缩包写到一半失败，临时数据库和元数据要删掉，否则下次列表里会出现一个打不开的备份。

内容寻址还有一个好处：同样的文件只存一份。用户反复备份同一本书，不会让备份目录线性膨胀。代价是清理逻辑更复杂，需要知道哪些 blob 还被引用。可以每次清理时重新扫描所有 manifest，虽然慢一点，但比维护引用计数不容易出错。

备份本身也要能验证。至少检查压缩包能否解开、数据库能否打开、关键表是否存在。只在创建时校验一次不够，用户真正需要恢复时才发现备份是坏的，那就太晚了。

## 四、恢复比备份更危险

备份失败，最多是没有备份。恢复失败，可能把现有数据弄没。

所以恢复最好分成几步：

- 先解压到临时目录，校验数据库的 `PRAGMA integrity_check`；
- 检查备份的 schema 版本，来自更新版本的备份直接拒绝，避免旧代码读到新表；
- 把当前数据移到 `.restore-old-*` 目录，而不是立刻删除；
- 换入新数据；
- 全部成功后再删旧目录。

中间任何一步崩了，下次启动会看到 `.restore-pending` 标记，把旧数据搬回来。标记里记录的旧目录必须在数据目录下面，并且目录名要以 `.restore-old-` 开头，避免标记被篡改后删到别的地方。

数据库本身打不开时，也可以走类似的路径：先把损坏文件改名成 `.corrupt-<时间>-reading-notes.db`，保留现场；再尝试恢复最近一份备份。恢复失败就把损坏库留在那里，绝不直接删掉。用户还有机会找工具修，或者至少知道文件在哪。

恢复前要确保数据库已经关闭，WAL 和 SHM 文件也处理掉。否则新数据库换进去，旧的 WAL 还在，SQLite 可能会把旧事务重放进来。

恢复完成后，索引、缓存、缩略图这些派生数据都应该失效。它们可以从主数据重建，但如果继续指向旧文件，就会出现“书恢复了，封面还是上一本”的问题。

恢复是一个高风险操作，界面上最好明确告诉用户：会替换当前数据、会先做一份安全备份、完成后需要重启。不要做成一个没有确认的按钮。

## 五、密钥和备份的关系

API Key 可以用 Electron 的 `safeStorage` 加密后存在设置文件里。备份会带上设置文件，但加密是跟系统账户绑定的。

所以把备份从一台电脑恢复到另一台，Key 往往解不开。界面上要提示“部分 API Key 无法在当前系统解密，需要重新填写”，不要假装恢复成功，也不要把明文写回去。

这不是一个很聪明的方案，但比把 Key 明文放进备份好。本地应用的便利和密钥安全之间，总要选一个。

## 六、路径校验也是数据安全

删除文件、恢复文件、导入压缩包，都会遇到路径。用户提供的 id、压缩包里的文件名、备份里的相对路径，都不能直接拼进 `fs.rm` 或 `fs.rename`。

一个简单的检查：

```ts
const target = path.resolve(root, ...name.split('/'))
if (target !== root && !target.startsWith(`${root}${path.sep}`)) {
  throw new Error('路径不安全')
}
```

这类检查不涉及 AI，也不酷，但它是“删除”这类操作的最后一道门。一个 `../../` 就可能删到数据目录之外。

压缩包还要额外小心。zip 里的文件名可能包含 `../`、绝对路径、Windows 盘符，甚至符号链接。解压时不能直接 `path.join`，要先规范化，再确认目标仍在临时目录内。

符号链接也要处理。一个指向数据目录外的 symlink，删除时可能会删到别的地方。可以在删除前用 `lstat` 判断类型，或者直接拒绝恢复包含符号链接的备份。

## 七、这些路径需要在测试里走一遍

正常流程很容易测：导入、编辑、删除、恢复、备份、还原。真正容易出问题的是异常路径。

可以准备几组测试：旧版本数据库升级、迁移中途失败、删除时文件移动失败、恢复时压缩包损坏、恢复中途进程退出、数据库文件损坏、备份里包含非法路径。每一组都应该有明确结果，而不是“看情况”。

这些测试不一定要自动化到 UI，但至少要在数据库和文件系统层跑通。很多数据丢失问题不是逻辑写错，而是异常分支没有走完。

## 八、上线前可以逐条检查

- schema 迁移是否只追加，不回头改旧迁移？
- 迁移是否在旧版本数据库上测试过？
- 删除操作是否有回收站或撤销？
- 删除前是否先保存了可恢复的数据？
- 备份是否包含数据库和书文件？
- 恢复前是否校验了数据库完整性和 schema 版本？
- 恢复中途崩溃是否能回滚？
- 损坏的数据库是否被保留，而不是直接删除？
- 文件路径是否做了目录边界校验？
- 跨机器恢复时，密钥无法解密是否有明确提示？

本地优先听起来很浪漫：数据是你的，工具也是你的。真正做起来，更多的是这些不浪漫的细节：迁移、快照、校验、回滚、回收站、路径校验。

判断一个本地功能是否可靠，不看它正常时多顺，而看它出错时用户还能不能回来。

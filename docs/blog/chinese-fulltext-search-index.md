# 中文全文搜索，先解决分词和索引，再谈向量

一个本地知识库，笔记少的时候，搜索就是一句 `LIKE '%关键词%'`。

几百条也没问题。等到书多了、AI 生成的读薄稿和卡片也进来，每次在搜索框里敲字都要扫一遍全库，输入开始有延迟。尤其是搜索“注意力”这种词，正文里出现几十次，`LIKE` 还要做模糊匹配，越用越慢。

这时候很容易想到两个方案：上 SQLite FTS5，或者上向量数据库。

两个都能解决问题，但都不是第一步。全文搜索首先要回答的是：用户输入的两个字，能不能稳定地命中他记得的那句话。

以下内容来自一个本地读书工具的实践。项目没有引入 FTS5，而是先写了一个内存倒排索引，把最明显的卡顿解决掉。它不是通用方案，但思路可以复用。

这不是说 FTS5 不好。如果数据量很大、需要短语查询、布尔查询、前缀匹配，或者希望把索引放在磁盘上而不是内存里，FTS5 更合适。它的问题是中文分词需要额外配置，打包和跨平台也要验证。对于几万条以内的本地笔记，一个简单的倒排索引已经够用。

## 一、中文为什么不能直接按空格分词

中文没有空格。英文可以按空格和标点切成词，中文不行。

最简单的办法是二元组（bigram）：把“注意力漂走”切成“注意”“意力”“力漂”“漂走”。

```ts
for (const match of normalized.matchAll(/[㐀-鿿]+/g)) {
  const run = match[0] ?? ''
  for (let index = 0; index < run.length - 1; index++) {
    tokens.add(run.slice(index, index + 2))
  }
}
```

二元组的好处是不需要词典，也不会因为新词、人名、术语切错。坏处是索引会变大，而且单字查询没有对应的 token。

所以单字查询可以走原来的 `LIKE` 兜底。搜索框里只输入一个字时，索引直接返回 `null`，调用方回退到数据库模糊查询。两个字以上才走索引。

英文和数字按词切，连字符和撇号也拆一下。比如 `well-being` 会同时索引 `well-being`、`well` 和 `being`，搜 `well` 也能命中。

二元组不是唯一的选择。也可以接一个中文分词词典，把“注意力”当成一个词，而不是“注意”“意力”。分词更准，但需要维护词典，遇到新人名、术语、网络词仍然会切错。二元组更笨，胜在稳定。

二元组的代价是索引膨胀。一段 N 个字的中文，大约会产生 N 个 token，而不是 N/2 个词。几万条笔记还可以放在内存里，几十万条就要重新考虑。可以给索引设一个上限，超过之后切换到磁盘索引或 FTS5。

归一化也要统一。查询和文档都要做 NFKC、大小写、全角半角处理，否则用户输入“ＡＩ”搜不到“AI”。但不要把繁简体强行合并，除非产品明确希望这样做。

## 二、倒排表用 id，不要用数组下标

索引的核心是一个 `token -> 文档 id 列表` 的 Map：

```ts
interface IndexCache {
  signature: string
  documents: SearchDocument[]
  byId: Map<string, SearchDocument>
  inverted: Map<string, string[]>
  tokensById: Map<string, string[]>
}
```

文档 id 用 `type:id`，比如 `note:abc`、`chapter:def`。用 id 而不是数组下标，是因为文档会增删，下标会变。早期用过数组下标，删除一条笔记后，倒排表里还留着旧位置，搜出来就是错的内容。

`tokensById` 是为了删除和更新时不用重新切分整篇文档。每个文档记住自己产生过哪些 token，删除时逐个清理。

内存索引的另一个成本是序列化。进程重启后如果每次都重新 tokenize，首次搜索会很慢；把索引写成压缩 JSON，加载会快很多。但 JSON 不是最快的格式，文件也可能损坏。加载时要校验版本和基本结构，失败就重建，不要让一个坏缓存把搜索整个卡死。

如果应用有多个窗口或多个进程，内存索引可能不是同一份。一个窗口更新了笔记，另一个窗口的索引还是旧的。可以让所有搜索都走主进程，或者用数据库签名做跨进程失效。不要在渲染进程里各自维护一份索引，否则迟早会出现搜索结果不一致。

## 三、怎么知道索引该不该重建

最笨的办法是每次搜索都全量重建，肯定不行。第二个笨办法是给每个写操作手动打标记，容易漏。

可以用 SQLite 的 `total_changes()` 做签名：数据库连接没变、总变更数没变，就认为索引没变。

```ts
const probe = conn.prepare('SELECT total_changes() AS n').get()
changes = Number(probe?.n ?? -1)
if (changes >= 0 && changes === cachedChanges && cachedSignature) {
  return cachedSignature
}
```

这个判断不完美。它只关心“有没有写入”，不关心写的是不是搜索相关内容；任何一次无关更新都会让签名变化。但它不会漏掉更新，对本地应用来说，宁可多重建一次，也不要搜到旧数据。

签名没变时，直接复用内存索引；进程重启后，从压缩的 JSON 文件加载。索引文件带版本号，版本不匹配就重建。加载时还要检查 token 和文档数量是否一致，避免读到半截损坏的缓存。

`total_changes()` 这种签名是“粗粒度”的。它只能告诉你数据库有没有变化，不能告诉你哪一行变了。好处是实现简单、不会漏；坏处是无关写入也会触发重建。如果写入很频繁，可以再加一层节流：签名变化后延迟几秒再重建，避免每输入一个字就重建一次。

如果数据库有多个连接，`total_changes()` 是连接级的，不是全局的。用连接池时，签名可能不准。要么固定用一个连接，要么改用版本号表或触发器维护全局变更计数。这个细节在单连接应用里容易忽略，换到多连接就会出问题。

## 四、增量更新，而不是全量重切

真正省时间的是增量更新。

索引失效时，先扫一遍数据库，拿到当前的文档列表。这个扫描本身不便宜，但比每次搜索都重新 tokenize 所有正文便宜得多。然后拿新列表和旧索引比：

- 新文档：切分，加入倒排表；
- 消失的文档：从倒排表移除；
- 内容没变的文档：跳过；
- 内容变了的文档：先移除旧 token，再加新 token。

判断“内容没变”要比较所有会影响搜索结果的字段：标题、正文、更新时间、所属书籍和章节、meta。少比一个字段，就可能出现“笔记改了但搜索还是旧内容”。

全量建索引时，每 40 个文档让出一次事件循环：

```ts
if (index % 40 === 39) {
  await new Promise<void>((resolve) => setImmediate(resolve))
}
```

这样大书库第一次建索引时，主进程不会长时间卡住，窗口还能响应。

增量更新最容易错的不是新增，而是删除和修改。删除时要清理该文档的所有 token；修改时要先删旧 token，再加新 token。顺序反了，倒排表里会留下重复 id，搜索结果就会出现同一条笔记多次。可以给每个文档的 token 列表做去重，也可以在加入时检查是否已经存在。

文档 id 也要稳定。如果每次保存都生成新 id，旧文档不会被识别为“修改”，而是“删除 + 新增”，索引会越来越大。用数据库里的主键做 id，不要用数组下标或时间戳。

## 五、先取交集，再打分

查询也切成 token。每个 token 在倒排表里有一组文档 id。所有 token 的 id 取交集，得到候选文档。交集为空就返回空，不再扫描。

候选文档再用一个很朴素的打分排序：

- 标题包含完整查询：+24；
- 标题包含某个 token：+6；
- 正文每出现一次 token：+2，最多算 12 次；
- 书 +8，章节 +2。

这个分数不精细，但比“按数据库默认顺序返回”好。搜索“注意力”时，标题里就有这个词的笔记会排在前面，正文里提了一嘴的排后面。

摘要不需要从数据库重新取，可以从索引里存的正文截一段。先找完整查询，找不到再找 token，前后各留几十个字符。这样搜索“注意力漂走”时，摘要能直接显示这两个词附近的句子。

这个打分只是启发式，不是 BM25。它能解决“标题命中排在正文命中前面”这种基本问题，但不能处理同义词、词频饱和、文档长度归一化。数据量小的时候够用；数据量大、搜索结果质量要求高时，还是应该换更成熟的索引。

还有一个常见需求是短语搜索。用户输入“注意力 漂走”，希望两个词连在一起出现。二元组索引只能保证两个 token 都存在，不能保证顺序。要支持短语，可以额外保存位置信息，或者在候选结果上再做一次字符串匹配。后者简单，但候选集不能太大。

## 六、语义搜索是另一件事

后来也加了语义索引，用 embedding 找“意思相近”的笔记。但它和全文搜索解决的不是同一个问题。

全文搜索要的是“我记得原话里有这个词”；语义搜索要的是“我不记得原话，但想找类似的观点”。前者要求准确、快、可解释；后者允许模糊，但需要模型和向量存储。

所以不要用语义搜索替换全文索引，而是让它们并存。全文搜不到时，再提示用户试试语义搜索。两个都不可用时，最后还有 `LIKE` 兜底。

## 七、什么时候该换方案

如果出现下面这些信号，说明内存倒排索引可能不够用了：

- 索引文件超过几百 MB，启动加载明显变慢；
- 需要短语、布尔、前缀、排序等高阶查询；
- 多进程或多设备需要共享索引；
- 搜索结果质量要求高，简单的打分不够；
- 中文分词错误成为主要投诉。

这时候再考虑 FTS5、专门的分词器或外部搜索引擎。向量索引仍然可以并存，但它解决的是语义召回，不是精确匹配。

测试查询也要覆盖真实输入：两个字的词、一个字的词、中英混排、带标点、带空格、很长的一句话、只输入拼音首字母。不要只测试“注意力”这种理想情况。

## 八、上线前可以逐条检查

- 中文是否按字或二字组切分，而不是按空格？
- 单字查询是否有兜底？
- 文档 id 是否稳定，删除后倒排表是否会残留？
- 索引失效的判断是否会漏掉更新？
- 是否有增量更新，而不是每次都全量重建？
- 大库首次建索引是否会让主进程卡住？
- 排名是否至少考虑了标题和正文的差异？
- 摘要是否能定位到查询词附近？
- 全文搜索和语义搜索是否说清楚了各自的边界？

这个索引不高级，没有分词词典，没有 BM25，也没有分布式。它只是把“每次输入都扫全库”变成了“先查倒排表，再给少量候选打分”。

但搜索的第一问题不是“要不要上向量数据库”，而是“用户输入的两个字，能不能稳定地命中他记得的那句话”。

这套索引只适合中小规模的本地数据，不是通用搜索方案。先把“两个字能不能搜准”解决，再谈语义，顺序会清楚很多。

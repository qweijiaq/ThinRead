# 长文本生成，不要指望一次请求跑完

上下文窗口变大之后，很多人会有一个很自然的想法：既然模型能读十万字，那就把整本书、整份报告、整章原文一次性塞进去。

第一次试的时候往往也能出结果。多试几次，就会遇到另一半问题：输出到一半断了，JSON 不完整，延迟从几十秒变成十几分钟，费用也上去了。再换一个模型，情况可能又不一样。

长上下文是能力，不是策略。真正要做的，是把长任务拆成可以失败、可以重试、可以解释的步骤。

以下内容来自一个读书笔记项目的实践。项目里要把一章几万字的正文“读薄”，再提炼卡片。最开始是一次请求，后来变成了一条流水线。下面按流水线的顺序，说说每一步为什么这么做。

## 一、一次请求的边界在哪里

一次模型调用能处理多长，不只取决于上下文窗口，还取决于：

- 输出预算。读薄稿本身要占输出 token，输入再长，留给输出的空间就越小；
- 延迟。长请求的首 token 时间更长，失败重试的成本也更高；
- 结构稳定性。输出越长，JSON 越容易在中途坏掉；
- 费用。输入和输出都按 token 计费，整章重试一次很贵。

所以判断“要不要拆”的标准，不是“能不能塞下”，而是“失败一次要不要重来”。

如果任务很短，一次请求最简单。如果任务需要几分钟、几十次调用，或者输出结构比较复杂，拆开通常更稳。

还有一个容易被忽略的数字：输出预算。模型的最大输出 token 是有限的，输入占掉越多，留给输出的空间越少。读薄一章不只是“读进去”，还要“写出来”。如果输入已经接近窗口上限，输出很容易被截断。

可以先粗算一下：原文 N 字，按 1.3 倍估输入 token，输出按 0.5 到 0.6 倍估，再加上系统提示和上下文。如果两者相加接近模型上限，就应该拆，而不是赌它这次能写完。

## 二、按结构切，不要按固定字数硬切

最省事的切法是 `text.slice(0, 6000)`。切点经常落在句子中间，模型拿到半句话，输出也会跟着断。

更好的做法是先看文档结构：标题、段落、列表、引用、代码块各自是块。按标题层级分出小节，再在 6,000 字以内合并成 chunk。一个 chunk 尽量是一个完整意思，而不是 6,000 个字符。

```ts
for (const section of sections) {
  if (section.text.length <= MAX_SECTION_CHARS) {
    chunks.push(section)
    continue
  }
  // 超长小节按段落对半拆，而不是按字符切
}
```

如果文档没有 HTML 结构，只能走纯文本，也可以按空行分段，再合并到目标长度。关键是尽量让切点落在段落边界，不要把一个论证切成两半。

代码块和表格要特殊处理。代码块最好整体保留，不要在中间切开；表格如果太大，可以按行分组，但每一组都带上表头，否则模型不知道每一列是什么。图片则更适合跟着它所在的小节走，而不是单独抽出来。

切分之后还要检查一遍：有没有 chunk 是空的，有没有只有标题没有正文，有没有两个 chunk 内容完全重复。这些看起来是小事，但会让模型把同一段内容压缩两次，最后合并出一份重复的稿子。

另外要有一个总上限。项目里纯文本回退时最多处理 60,000 字，超过就截断。这个上限不是为了效果最好，而是为了避免一次任务跑太久、费用失控。用户需要知道这次只处理了前一部分。

## 三、并发、重试和超时

拆成 chunk 之后，可以并发处理。项目里开了 4 个 worker，每个 chunk 独立请求，最多重试 3 次，退避时间是 600ms、1200ms。

```ts
for (let attempt = 0; attempt < 3; attempt++) {
  try {
    return await condenseChunk(model, args, chunk, signal)
  } catch (error) {
    if (signal.aborted) throw error
    if (isTimeoutError(error)) break
    if (attempt < 2) await retryDelay(attempt)
  }
}
```

超时是特殊情况。超时通常说明请求本身太大，原样重试大概率还是超时，所以遇到超时不再重试，直接把 chunk 按段落对半拆开，两半各试一次。

拆半也有边界：如果两半里有一半少于 80 个字，就不拆了，避免切出一堆没有意义的碎片。

并发数不是越高越好。服务商可能限流，本地也可能同时跑别的任务。4 个是一个折中值，不是定理。

如果服务商返回 429，重试时间最好带一点随机抖动，避免所有 worker 在同一秒再次撞上去。重试也要区分错误类型：网络超时、限流、鉴权失败、内容超长，处理方式完全不同。鉴权失败重试多少次都没用，内容超长应该拆块，限流才值得等一等。

还有一点：重试的请求最好只读，不要带副作用。生成文本通常没问题，但如果一次请求会写文件、发消息、扣款，就不能简单地“失败再来一次”。

## 四、检查点：失败后不要从头再来

这是整个流程里最值得做的一步。

读薄一章，可能要跑十几个请求。如果第 18 块失败，前面 17 块都白跑，用户重试一次又要重新付费。所以每完成一个 chunk，就把结果写进检查点文件。

检查点的 key 不是章节 id，而是 `标题 + 图片签名 + 正文` 的哈希。正文没变，下次就能直接复用。

```ts
checkpoint.set(chunkKey, result)
persistCheckpoint()
```

检查点是中间状态，允许不完整；最终缓存只有在没有降级步骤时才写。两者分开，避免“半成品”被当成完整结果。

这个设计有一个直接好处：失败后重试，只补失败的块。用户不需要知道哪些块成功了，但账单会知道。

检查点写入要尽量原子。先写临时文件，再 `rename` 到目标位置，避免进程在写到一半时被杀，留下一个无法解析的 JSON。检查点还要有有效期，太旧的中间结果可能对应一套已经变了的 prompt 或模型，继续复用反而会出问题。

检查点不是最终缓存。它只保存“这一块已经压缩过”的中间结果，不保存卡片、回查和报告。最终缓存要等整个流程成功、没有降级步骤时才写。两者混在一起，很容易把半成品当成完整结果。

## 五、全部失败时，不要伪造成功

有一类错误很隐蔽：所有 chunk 都失败了，但代码把原文当成 `compressed` 塞回去，继续往下走。最后用户看到一份“读薄稿”，其实就是原文，只是换了个标题。

正确的做法是：如果失败的 chunk 数等于总数，直接抛错，不写任何结果。

```ts
if (condenseFailed >= chunks.length) {
  throw new Error(`读薄失败，没有写入任何笔记：${reason}`)
}
```

部分失败则允许继续，但要在报告里记一条 `degraded`，说明哪个阶段失败了几块。界面上不要把它包装成完整成功。

用户可以选择重试，也可以接受一份不完整的稿子，但不能在不知情的情况下接受。

降级报告最好具体到阶段和数量，而不是一句“部分失败”。比如“压缩阶段 22 块中失败 3 块，回查未执行”，用户才知道该不该重试。如果失败的是关键阶段，比如所有压缩都失败，就不应该进入后续步骤，直接报错更诚实。

失败也要分类。超时、限流、鉴权、内容超长、返回格式错误，对应的下一步不一样。把所有错误都显示成“生成失败，请重试”，用户只能反复点按钮。

## 六、合并顺序比完成速度重要

并行压缩的结果不能按完成顺序拼。哪个 chunk 先回来，取决于网络和模型，和原文顺序无关。

每个 chunk 都带着 `sectionIndex`，合并时按原小节索引归位。同一小节如果有多个 chunk，再按 chunk 在原文里的顺序拼。这样读薄稿的段落顺序和原文一致，后面的卡片提取才有稳定的上下文。

合并之后才开始提卡片。卡片和回查可以并行：回查要重新看原文，卡片只看读薄稿，两者互不依赖。延伸（每张卡片最多 3 条）又在卡片完成之后开始，尽量和还在跑的回查重叠。

## 七、档位不是参数，是流程

很多产品会有一个“快速/标准/精读”的选择。如果只是把同一个 prompt 换个温度，档位的意义不大。

真正有区别的档位，改变的是流程：

- 快速：只做读薄和卡片，不回查，不延伸；
- 标准：读薄、卡片、回查、延伸；
- 精读：在标准基础上再加一轮细节回查。

卡片数量的范围也可以按读薄稿字数算，不是固定 10 张。快速模式跳过回查和延伸，少两次请求；精读模式多一次细节回查，换更完整的覆盖。

这些差异应该写进生成报告，让用户看到这次用了哪个档位、多少 tokens、耗时多久。不是所有任务都值得用最贵的流程。

## 八、Prompt 缓存也影响账单

同一章重试时，系统提示和原文前缀通常是一样的。对于支持前缀缓存的服务商，把这部分放在前面可以命中缓存；有些服务商需要显式标记，有些会按相同前缀自动命中。

但缓存不是免费的。写入缓存可能要多付钱，如果只写不读，反而更贵。所以是否启用缓存要看使用模式：同一段材料会被反复处理，缓存才划算；一次性任务，缓存可能只是增加成本。

缓存命中也应该被记录。它没有产生新的调用，但确实省下了 token。统计页把“实际花费”和“缓存节省”分开显示，用户才能判断这个月的账单为什么和预期不一样。

## 九、上线前可以逐条检查

- 切分是否尽量落在段落或小节边界？
- 是否有单次处理的字数上限？
- 并发数是否可配置，是否考虑了限流？
- 超时和普通失败是否分开处理？
- 失败后是否能从检查点继续？
- 全部失败时是否会明确报错，而不是写入假结果？
- 部分失败是否在报告里可见？
- 合并是否按原始顺序，而不是完成顺序？
- 不同档位是否真的改变了流程？

这套流程在这个项目里够用，但不一定适合所有长文本任务。短任务、结构简单的任务，一次请求可能更便宜。真正需要流水线的，是那些跑到一半会失败、失败一次很贵、用户还会回来的场景。

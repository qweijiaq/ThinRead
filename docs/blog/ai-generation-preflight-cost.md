# AI 产品的成本，应该在使用前就可见

有一次手滑点了一个生成按钮。

不是很大的事，一章而已，几毛钱。但那一刻意识到：用户在这个界面上，其实不知道点下去会发生什么。用哪个模型、发多少字、大概花多少钱、会不会把整本书传出去，都没有一个地方说清楚。

后来加了一个预检弹窗。点“生成”之后，先不请求模型，而是显示一张小卡片：

- 模型和服务商；
- 快速 / 标准 / 精读；
- 预计输入和输出 tokens；
- 预计费用；
- 这次会发送多少字、几张图；
- 一句“数据仍保存在本机”。

用户确认后才开始。可以勾选“本次会话不再提示”，下次同一个模型、同一个档位就不弹了。

预检也会打扰用户。每次点击都弹窗，很快就会变成“看都不看就点确认”。所以抑制机制要按“模型 + 档位”记住，而不是永远不再提示；换了更贵的模型，还是应该提醒一次。

另一个取舍是：预检放在点击后、请求前，还是放在设置里？放在点击后更贴近使用场景，但会多一步；放在设置里不打扰，但用户不会每次看到。比较稳的是“第一次或高成本操作时弹，低成本的重复操作可以跳过”。

以下内容来自一个读书工具项目的实践。预检只是第一步，后面还补了本地用量统计和缓存节省。下面按“事前、事中、事后”说说这套东西怎么落地。

## 一、估算不是报价

token 数怎么估？

精确算法需要 tokenizer，不同模型还不一样。为了一个预检弹窗引入几套 tokenizer，不划算。可以用一个很粗的公式：

```ts
const inputTokens = Math.ceil(chars * 1.35 + 1_800 + images * 900)
const outputTokens = Math.ceil(Math.max(1, chars) * 0.6)
```

1.35 是中文正文的经验系数，1,800 是系统提示和上下文的固定开销，每张图按 900 tokens 算。输出按原文的 0.6 倍估。

这些数字肯定不准。有的模型中文 token 效率高，有的低；图片按分辨率算，不是按张算；输出长度也取决于内容密度。

所以弹窗里要写“预计”，不是“本次消费”。真正的费用以服务商账单为准。用户需要知道这是一个量级，不是承诺。

如果条件允许，可以显示一个区间，而不是一个精确数字。比如“约 2,000–3,000 tokens，预计 ¥0.02–0.05”。区间比单点更诚实，也更容易解释误差。

有些产品会内置 tokenizer，按真实模型计算。这样做更准，但维护成本高，模型一换就要更新。预检的目标是“让用户心里有数”，不是“财务对账”。在准确性和复杂度之间，可以先选简单方案，等用户真的需要再升级。

## 二、价格是用户填的，不要猜

模型价格变化很快，内置一张价格表，过两个月就可能不准。更麻烦的是，不同服务商、不同地区、不同套餐价格不一样。

所以价格可以来自设置里用户自己填的“每百万 token 输入/输出价格”。没填就显示“未填写价格，无法估算”，不要假装知道。

这看起来是把麻烦推给用户，但比给一个错误数字好。用户如果在意费用，会去填；不在意，也不会被一个假报价误导。

价格未知时，仍然可以让用户继续，但要明确写“无法估算金额”。不要因为没填价格就阻止生成，也不要用一个默认价格假装精确。产品可以提供“去填写价格”的链接，把选择权交给用户。

如果服务商有免费额度，也可以提示“本次可能消耗免费额度”。这比直接显示 ¥0 更准确，因为免费额度用完后仍然会收费。

订阅制的服务商不按 token 计费，代码里可以直接跳过金额估算，只统计 tokens。这个例外也要写进逻辑，不然会算出一个根本不存在的账单。

价格单位也要写清楚。是人民币还是美元，是每百万 token 还是每千 token，输入和输出是否同价。用户填错单位，估算会差几个数量级。设置页最好给出一个示例，而不是只放两个空输入框。

税费、汇率、服务商的阶梯价，预检通常算不进去。这些可以在说明里提一句，避免用户把预检金额当成最终账单。

## 三、“会发送什么”比价格更重要

预检弹窗里应该有一块“会发送什么”：

> 本章正文约 12,000 字，2 张图片，会发送给你配置的模型服务商。书和笔记本身仍保存在本机。

这句话不是装饰。很多用户对“本地优先”的理解是“所有东西都不出电脑”，但调用云端模型时，正文一定会发出去。把这句话放在点击之前，比放在隐私政策里有用。

如果是演示模式，不调用真实模型，预检可以直接跳过。演示模式下的结果是内置样例，界面上要标“演示样例”，分享按钮也要禁用，避免把样例当成真实内容发出去。

“会发送什么”最好具体到范围和来源。比如“当前章节正文、2 张插图、最近的 3 条笔记”，而不是笼统的“相关数据”。用户看到具体内容，才知道自己能不能接受。

如果产品支持“只发送选中段落”或“排除图片”，预检里也可以提供这些选项。让用户在选择发送范围的同时看到成本变化，比事后去设置里找开关更直观。

## 四、用量统计不要记录正文

预检只是事前。事后还需要知道：这个月到底花了多少，哪个步骤最贵，缓存省了多少。

主进程可以把每次模型调用写成一行 JSONL：

```json
{"step":"chapter-notes","model":"...","inputTokens":1234,"outputTokens":567,"durationMs":8000,"ok":true}
```

只记录步骤、模型、耗时、token 和错误，不记录 prompt，也不记录正文。统计页读这些文件，按天、按模型、按步骤汇总。

有两个细节容易算错：

第一，读薄一章会调用多个子步骤，最后还有一条汇总行。如果汇总行也计入 token，就会双计。所以汇总行要带 `aggregate: true`，统计时跳过。

第二，本地缓存命中没有调用模型，但省下了 token。缓存命中单独记一条 `cached: true`，并记录省下的 token 和估算金额。这样统计页能显示“缓存省了多少钱”，而不是只看到总支出。

统计还要能按任务拆分。用户想知道“这个月是生成贵，还是翻译贵”，只看一个总数不够。按步骤聚合之后，才能发现哪个功能值得优化。

日志也要有保留期限。一年前的 trace 对排查问题意义不大，却会一直占空间。可以按天切割文件，启动时清理过期文件，并提供一个“清空用量数据”的入口。

## 五、缓存和价格要分开算

缓存命中不代表免费。它只是没有产生新的模型调用。

如果服务商对缓存写入收费，或者缓存读取有折扣，估算时要按实际规则算。不要把“缓存命中”直接等同于“这次没花钱”。

同样，失败请求也可能产生费用。统计里要区分调用次数、失败次数和实际 tokens，不要只用一个“总费用”概括。

## 六、成本显示之后，使用习惯会变

这是很多人没预料到的。

以前生成一章不太看成本，反正就是“几毛钱”。有了预检和统计之后，用户会开始选档位：只是快速看一遍，用快速模式；要写文章，用标准；特别重要的章节才用精读。

这不是因为用户在意那几毛钱，而是因为成本变得可见了。可见之后，选择才有意义。

## 七、给用户一个上限

预检解决的是“这一次大概花多少”，不解决“这个月会不会失控”。

可以给产品加一个预算上限：按天、按任务或按次设置最大费用，超过时提示用户，而不是继续调用。上限不必很精确，但要有。

对于整本生成、批量翻译这种任务，还可以显示“已花费 / 预计总花费”。用户看到跑了 18/30 章、花了多少钱，才知道要不要继续。

预算用完后，不要静默失败。告诉用户是因为达到上限而停止，并保留已完成的部分。

## 八、按任务拆分成本

同一本书，读薄、卡片、回查、翻译、排版，成本差别很大。只显示一个总额，用户不知道钱花在哪。

可以按步骤记录 tokens 和费用，在统计页展示“读薄占 60%，翻译占 25%”。这样用户想省钱时，知道该关哪个功能；开发者想优化时，也知道该看哪一段。

步骤名要稳定，不要用临时字符串。否则同一个功能在不同版本里叫不同名字，统计就没法比较。

## 九、成本数据还可以用来做产品决策

统计不只是给用户看的，也能帮助产品决定默认值。

如果发现大多数用户只用快速模式，标准模式很少被打开，可能说明默认档位太重；如果精读模式的失败率明显更高，可能需要降低并发或缩小单次处理量；如果翻译成本远高于读薄，预检里就应该更突出翻译的预计费用。

这些判断不需要精确的财务数据，只需要趋势。关键是不要把统计做成一个“总金额”数字，而要能按功能、模型、步骤拆开。

成本也不应该成为唯一指标。更便宜的模型可能带来更多重试，最终总成本反而更高；更贵的模型可能一次成功，用户时间更省。预检和统计的作用是让这些取舍可见，不是替用户做决定。

## 十、上线前可以逐条检查

- 用户点击前是否知道用的是哪个模型、哪个档位？
- 是否显示了预计输入/输出 tokens？
- 是否显示了预计费用，或者明确说明“未填写价格，无法估算”？
- 是否说明了这次会发送什么内容？
- 是否说明了数据仍然保存在本机？
- 演示模式是否不调用真实模型，并且标记了样例？
- 用量统计是否避免记录 prompt 和正文？
- 汇总行是否避免了重复计数？
- 缓存命中是否单独统计？
- 订阅制或特殊计费是否被排除在金额估算之外？

预检弹窗不是一个很“AI”的功能。它不提升生成质量，也不减少幻觉。它只是把一次调用前的信息摊开：用什么、发什么、大概花多少。

但 AI 产品很容易让人产生“点一下没什么”的错觉，直到账单出来。

这些估算和统计只是一个项目里的取舍，不同产品可以更简单。重要的不是数字多精确，而是用户在点击之前，知道自己在为什么付费。

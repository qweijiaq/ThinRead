# 文档翻译，别把 HTML 交给模型

整章翻译的第一版通常很直接：把章节的纯文本发给模型，让它翻成目标语言，再把结果按段落包成 `<p>`。

翻出来的文字没问题，排版全没了。标题变成了普通段落，列表变成了连续句子，表格里的单元格被压成一行。用户看到的是“翻译了，但没法读”。

第二版更直接：把整段 HTML 字符串发给模型，让它保留标签翻译。结果更糟——模型开始自己补 `<div>`、丢 `<span>`，代码块里的尖括号被当成标签吃掉。

问题不在于模型不会翻译，而在于我们给它的任务边界不清楚。模型擅长翻译句子，不擅长在翻译的同时维护一套标记语言。

以下内容来自一个读书工具项目的实践。项目要翻译整本书，保留标题、列表、表格和代码块。最后采用的思路是：不翻译 HTML，只翻译 HTML 里的文字，然后放回原来的位置。

## 一、先找出真正承载文字的块

一篇文章里，真正需要翻译的是这些块：

```ts
const BLOCK_SELECTOR =
  'h1,h2,h3,h4,h5,h6,p,li,blockquote,figcaption,td,th,dt,dd,caption'
```

每个块只取自己的文字，记下它在 DOM 里的位置。翻译完成后，只替换块的 `innerHTML`，外面的标签、class、表格结构都不动。

```ts
const blocks = collectBlocks(html)
const batches = batchBlocks(blocks)

for (const batch of batches) {
  const texts = batch.map((index) => blocks[index].text)
  const translated = await translateTexts(model, texts)
  // 按原位置写回
}
```

这样做的前提是：块内部没有复杂的嵌套结构。遇到行内代码、链接、加粗，不能把标签直接发给模型，否则模型很容易改坏。

块的选择也要避免重复。`li > p` 和 `td > p` 会让同一个文字被翻译两次，所以只处理叶子块：如果这个块里还有别的块级元素，就跳过它。包含 `img`、`svg`、`pre` 的块也最好跳过，避免把图片和代码混进翻译请求。

表格是最容易出问题的结构。行和列的顺序、表头、合并单元格，都不能靠模型重新生成。只翻译单元格里的文字，表格本身不动，是最稳的做法。

## 二、行内代码用占位符保护

翻译前，先把块里的 `<code>` 内容替换成占位符：

```text
请运行 ⟦C0⟧ 命令，然后打开 ⟦C1⟧。
```

模型只需要知道“这里有一个不能翻译的东西”，不需要看到真实的代码。返回后，再把占位符换回 `<code>` 标签，内容转义。

```ts
const codes: string[] = []
clone.find('code').each((index, code) => {
  codes.push($(code).text())
  $(code).replaceWith(`⟦C${index}⟧`)
})
```

这一步还有一个好处：代码、URL、变量名不会被模型“顺手翻译”。以前出现过 `useEffect` 被翻成“使用效果”，看起来很好笑，但确实会发生。

链接和加粗要不要保留，是一个取舍。项目里没有单独保留，块里的它们会被压成纯文字。行内标签一旦交给模型，很容易被改坏；而代码是绝对不能翻的，所以只给代码做占位符。丢掉的链接样式由外层排版兜底。

占位符本身也要选一个正文里不会出现的格式。`⟦C0⟧` 比 `[[0]]` 更安全，因为后者可能和 Markdown 链接冲突。还原时要做转义，避免代码里的 `<`、`>` 被当成标签重新插进 DOM。

如果产品非常依赖链接和脚注，就不能简单压平。可以把链接拆成“文字 + URL 列表”，让模型只翻文字，返回后按顺序重新组装。这样做更复杂，但能保留跳转。

## 三、一次翻一批，但要求返回 JSON 数组

如果每个块发一次请求，一章可能有几十次调用，慢且贵。可以把块按 5,000 字、最多 24 个块分批。

一批发过去，要求模型返回一个字符串数组，长度和输入一致：

```json
["第一段译文", "第二段译文", "..."]
```

返回后检查数组长度。长度不对就重试一次，并在 prompt 里明确说“上一次没有返回合法的 JSON 数组，请严格返回 N 个字符串”。还不对就整批失败。

为什么不用对象或带 id 的结构？数组最简单，顺序就是对应关系。块本身已经有顺序，不需要模型再生成 id。模型少写一个字段，就多一种失败方式。

分批大小也要权衡。太小，请求次数多、上下文少；太大，输出容易截断、失败重试成本高。5,000 字、24 个块是一个折中值。可以按目标语言调整，比如中文翻英文，输出通常会变长，批次要适当缩小。

提示里最好带上书名、章节名和前后文主题。模型知道这段在讲什么，专有名词的翻译会更一致。但不要把整章都塞进去，否则又回到了“一次请求处理太长”的问题。

## 四、整批失败时，逐段兜底

一批里有一两个块翻译失败，整个批次重试也不一定有用。所以整批失败后，可以退化成逐块请求：

```ts
try {
  translated = await translateTexts(model, args, texts)
} catch {
  translated = []
  for (const text of texts) {
    try {
      const [single] = await translateTexts(model, args, [text])
      translated.push(single ?? text)
    } catch {
      translated.push(text)
    }
  }
}
```

翻不出来的块保留原文，至少不会让整章变成空白。用户能看到哪一段没翻，也能单独重试。

这不算优雅，但它把“整章失败”变成了“局部失败”。

逐段兜底的成本会高一些，因为请求次数变多。可以只对失败的批次做逐段重试，而不是整章都逐段。重试前先记录哪些块已经成功，避免重复翻译同一段。

翻不出来的块保留原文，界面上最好有标记。用户看到一段外文混在译文里，比看到一段被模型胡乱改写的中文更好。

## 五、纯文本回退也要有

有些旧文档没有可用的 HTML，只有纯文本。这时候走另一条路径：按段落切块，逐块翻译，最后包成 `<p>`。

这条路径会丢标题层级，但至少不会因为找不到块而直接报错。代码里先判断 `blocks.length === 0`，再决定走 HTML 还是纯文本。

## 六、只给需要翻译的文档显示入口

翻译按钮不必对所有文档都显示。判断依据可以是整篇文档的正文语言：如果主要是目标语言，就不显示“翻译”和“重新翻译”。

这个判断也用在单章翻译上。用户打开一篇中文文章，点翻译，会得到“这一章看起来已经是中文，不需要翻译”，而不是让模型把中文再翻一遍。

语言判断不可能百分之百准确。中英混排、引用很多的文档，可能会误判。所以入口只是隐藏，不是禁用；真有需要，用户仍然可以从菜单里找到。

判断语言时，不要只看前几段。书名、版权页、引用块可能都是另一种语言。更稳的做法是统计正文里目标语言和非目标语言的字符比例，再给一个阈值。低于阈值时，宁可让用户手动确认，也不要直接隐藏入口。

## 七、旧译文顺手升级

早期版本的译文可能只有纯文本，没有 HTML 结构。后来数据库加了 `translated_html` 字段，全书翻译时会检查：如果一章只有旧译文、没有结构化译文，就重新翻一遍，顺手升级。

这样用户不需要手动清理旧数据。翻译任务会跳过已经有结构化译文的章节，不会重复花钱。

## 八、翻译质量怎么检查

翻译完成后，至少做几项自动检查：

- 返回数组长度是否和输入一致；
- 每个块是否为空，是否只剩占位符；
- 代码占位符是否全部还原；
- 表格单元格数量是否变化；
- 标题层级是否还在；
- 有没有整段直接返回原文。

这些检查不能保证翻译准确，但能抓住大部分结构性问题。剩下的准确性，可以抽样让模型自评，或者让用户标记“这段翻得不对”。不要用单一指标骗自己，文档翻译更看重术语一致和结构完整。

## 九、术语和上下文要跨批次保持一致

分批翻译最大的问题是上下文断裂。同一个术语，第一批翻成“注意力”，第二批翻成“专注力”，读者会以为这是两个概念。

解决办法不是把整本书塞进一次请求，而是维护一份术语表。书名、作者名、章节标题、反复出现的关键词，可以提前提取出来，作为提示的一部分传给每一批。术语表不需要很大，几十个词就够用。

如果术语表也没有，可以在 prompt 里要求“同一术语在全文保持一致”，但模型看不到全文，效果有限。更好的做法是翻译完成后做一次一致性检查：统计同一原文词对应的译文，出现多种译法时提示用户。

上下文也可以按章节组织。每一批带上章节标题和前后段摘要，模型至少知道这一段在讲什么。摘要可以由上一批的译文生成，成本不高，但能明显减少指代错误。

## 十、上线前可以逐条检查

- 翻译的是文字，还是整段 HTML？
- 块的选择是否覆盖标题、列表、表格、引用和代码？
- 行内代码是否用占位符保护？
- 占位符是否会在返回后正确还原并转义？
- 批量请求是否检查了返回数组的长度和顺序？
- 整批失败时是否有逐段兜底？
- 没有 HTML 时是否有纯文本回退？
- 已有译文是否会跳过，旧译文是否会升级？
- 语言判断不确定时，用户是否还能手动触发？

整章翻译看起来是“把一种语言换成另一种语言”，实际做起来，大部分工作是在保护结构：标题还是标题，表格还是表格，代码还是代码。

模型很擅长翻译句子，也很擅长在翻译的时候“顺手整理”它觉得不重要的标签。任务边界要划清楚：只翻该翻的部分。

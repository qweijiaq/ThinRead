# 流式输出不是万能药：哪些 AI 结果可以边生成边展示

用户看到文字一个字一个字出来，会觉得应用很快。

于是很容易产生一个想法：所有 AI 请求都应该流式。聊天要流，总结要流，结构化数据也要流。把 `generateText` 换成 `streamText`，似乎就完成了。

实际做起来，流式带来的复杂度不比它解决的问题少。流式只影响展示，不应该影响状态机。哪些结果可以边生成边展示，哪些必须等完整结果，值得分开想。

以下内容来自一个读书工具项目的实践。项目里有聊天、问答、自测和结构化生成，几种场景对流的处理并不一样。

## 一、流式只改变展示，不改变语义

一次模型调用，不管是否流式，本质上仍然是一次请求。模型最终会返回一段完整内容，或者一个完整的工具调用。

流式做的事情，是把这段内容分块送到前端，让用户更早看到。

```ts
const stream = streamText({
  model,
  system,
  prompt,
  abortSignal,
})

for await (const chunk of stream.textStream) {
  emit(chunk)
}
```

但“更早看到”不等于“更早完成”。在流结束之前，你不知道模型会不会中途报错，也不知道最终的结构是否完整。

所以状态机应该按完整响应来设计：

- 请求开始：状态为 running；
- 收到增量：只更新预览，不写入最终结果；
- 流正常结束：解析、校验、落盘；
- 流出错或中止：标记失败或暂停，不把半截内容当成完整结果。

如果把每个增量都当成一次“成功”，用户刷新后可能会看到一段不完整、也没有错误提示的内容。

还有一个常见误解：流式会让生成更快。它只是让第一个字更早出现，总耗时通常不会减少，甚至可能因为分块传输略慢。用户感知变好了，服务器和 token 成本没有变。

所以不要为了“看起来快”而给所有请求加流式。短请求、结构化请求、后台任务，等完整结果反而更简单。

## 二、纯文本可以流，结构化结果要小心

聊天最适合流式。用户问一句，模型答一句，文字越长，流式带来的感知提升越明显。即使中途断了，用户也能看到已经生成的部分。

结构化结果就没那么直接。比如让模型返回：

```json
{
  "answer": "...",
  "citations": ["..."]
}
```

流式输出到一半时，JSON 通常是不合法的。你不能在第一个 token 到达时就去 `JSON.parse`，也不能保证后面的字段会出现。

有两种处理方式。

第一种，把结构化结果当成“普通文本”流给用户看，但在流结束后才解析。解析失败就重试或报错，流过程中的内容只作为预览。

第二种，使用支持“部分结构化输出”的接口，让模型在生成过程中逐步给出合法对象。比如某些 SDK 提供 `partialOutputStream`：

```ts
const stream = streamText({
  model,
  output: Output.object({ schema }),
})

for await (const partial of stream.partialOutputStream) {
  onDelta(partial?.answer ?? '')
}

const final = await stream.output
```

这种方式体验更好，但不是所有服务商都支持。代码里仍然要保留“流结束后再解析”的兜底。

部分结构化输出也有坑。`partial` 里的对象可能只有一半字段，数组可能只到第一个元素。展示层可以只取已经稳定的字段，比如 `answer`，不要拿 `citations` 去做跳转，因为后面可能还会变。

最终结果仍然要通过 schema 校验。流式只是提前展示，不是跳过校验的理由。校验失败时，最好保留原始文本，方便排查是模型输出问题，还是解析器问题。

## 三、不要一边流一边写数据库

一个常见的错误是：每收到一个增量，就把内容写进数据库。这样用户刷新后能看到“进度”，但也会带来几个问题：

- 写入频率太高，数据库压力大；
- 半截内容可能被当成完整结果；
- 如果流失败，数据库里留下一个没有错误标记的半成品；
- 多个请求并发时，可能互相覆盖。

更好的做法是：流式内容只放在内存或临时状态里，等完整结果通过校验后再落盘。落盘时写完整内容，并记录状态、模型、用量和错误信息。

如果确实需要“崩溃后恢复半截内容”，可以单独存一个草稿或检查点，并明确标记“未完成”。不要和最终结果混在同一张表里。

草稿也有一个好处：用户可以在生成过程中编辑。比如一边流式返回，一边让用户修改提示或切换模型。但这时候要处理版本冲突，确保最终落盘的是用户确认的那一版，而不是后台还在跑的那一版。

如果多个请求并发，最好给每次请求一个 id。前端只接受当前 id 的增量，旧请求晚到的内容直接丢弃。否则用户切换了会话，旧回答还会拼到新回答里。

## 四、服务商不支持流式怎么办

有些 OpenAI-compatible 服务不支持结构化流式输出，或者流到一半返回错误。代码里不能假设“流一定可用”。

一个实用的降级策略是：

```ts
let emitted = false

try {
  const stream = streamText({ model, prompt })
  for await (const chunk of stream.textStream) {
    emitted = true
    onDelta(chunk)
  }
  return await stream.output
} catch (error) {
  // 还没有产生任何可见输出时，可以安全地回退到普通请求
  if (emitted) throw error
}

return await generateText({ model, prompt })
```

关键点是“是否已经产生了可见输出”。

如果还没有输出，回退到普通请求是安全的，用户不会看到重复内容。如果已经输出了一部分，再回退重放，用户会看到两遍开头，甚至可能触发两次副作用。

这个判断也适用于重试。已经流出的内容不能当作没发生。

降级也要看错误类型。如果是模型不支持结构化流式，回退到普通请求通常没问题；如果是鉴权失败、余额不足、内容超长，回退也救不了，应该直接告诉用户原因。把错误翻译成可执行的提示，比反复重试有用。

## 五、中止、超时和重试

流式请求更需要中止信号。

用户切换会话、关闭面板、按 Esc，都应该停止当前请求。中止信号要传到模型请求和后续处理里，而不是只在前端把 UI 关掉。

```ts
const signal = AbortSignal.timeout(90_000)
const stream = streamText({ model, prompt, abortSignal: signal })
```

超时也一样。流式请求可能一直有零碎的 token 返回，看起来“还在跑”，但实际上已经超出了可接受的时间。最好设置一个总超时，而不是只看“有没有新 chunk”。

重试要区分阶段：

- 请求还没开始，或还没有任何可见输出：可以安全重试；
- 已经输出了一部分：不要重放，应该告诉用户“这次生成中断了”，让用户决定是否重新生成；
- 已经执行了工具调用：更不能重放，避免副作用执行两次。

中止信号要一路传下去。模型请求、工具执行、文件写入、后续的解析和落盘，都应该检查同一个 signal。只在最外层 `abort`，内层还在跑，用户会看到“已停止”但后台还在花钱。

中止之后还要清理。已经建立的事件监听、定时器、临时文件、请求 id，都要释放。否则下一次请求可能收到上一次的残留事件。

## 六、流式内容和最终状态要能对上

用户看到的文字，和数据库里保存的结果，最好是一致的。

如果流式过程中做了一些“展示层加工”，比如过滤 Markdown、隐藏思考过程、把引用变成角标，最终落盘时也要保存原始内容，或者保存加工后的内容并记录版本。否则用户刷新后看到的内容会和刚才不一样。

对于聊天，可以保存完整的 assistant 消息，而不是每个增量。对于结构化结果，保存解析后的对象和原始文本，方便排查。

还有一个细节：流式过程中，前端可能会对增量做拼接。如果网络乱序、重复发送，拼接结果会错。增量协议最好带序号，或者保证同一请求的增量是顺序的。

## 七、怎么测试流式

流式不好测，因为它依赖时间。可以准备几类用例：

- 服务商正常返回，但每个 chunk 之间间隔很长；
- 流到一半断开；
- 结构化输出在某个字段后中断；
- 用户在中途取消；
- 多个请求并发，旧请求晚到；
- 服务商不支持流式，直接报错。

测试的重点不是“文字有没有出来”，而是“状态有没有正确收尾”：取消后是否停止、失败后是否保留错误、刷新后看到的是完整结果还是明确的未完成状态。

如果 UI 测试不方便，可以在主进程层 mock 一个流，手动控制 chunk 的发送和错误。比直接打真实模型稳定得多。

## 八、上线前可以逐条检查

- 流式是否只影响展示，最终状态是否仍然按完整响应处理？
- 结构化输出是否等流结束后才解析？
- 是否支持服务商不支持流式时的降级？
- 降级是否只在“没有可见输出”时发生？
- 用户中止后，模型请求是否真的停止？
- 是否有总超时，而不是只看有没有新 chunk？
- 增量内容是否避免直接写入最终结果表？
- 刷新或崩溃后，用户看到的是完整结果、草稿，还是明确的失败状态？
- 展示层加工后的内容，和落盘内容是否一致？

流式是一个很好的体验优化，但它不是“把请求换个 API”那么简单。它把一次完整的请求拆成了很多个可能失败的时刻，状态管理必须跟上。

能流的时候流，不能流的时候老老实实等结果。用户不一定在意文字是不是一个个出来，但一定会在意刷新之后内容还在不在。

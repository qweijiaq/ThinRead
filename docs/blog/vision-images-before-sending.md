# 多模态应用里，图片不是“丢给模型”就行

书里有一张架构图，正文用两段话描述它。问模型图里有什么，它说“我看不到图片”。

这时候才意识到，多模态不是“模型支持图片”这么简单。图片得先被找出来、压缩、控制数量、附上上下文，还要避免把装饰图也发过去。任何一个环节没做好，用户看到的都是“模型在胡说”。

以下内容来自一个读书工具项目的实践。项目要把章节里的图表、流程图、表格截图发给视觉模型，帮助生成读薄稿和卡片。下面这些处理，大部分是踩坑之后补上的。

## 一、先判断这个模型到底能不能看图

不同服务商的模型命名没有统一标准。写一个“支持视觉”的列表，很容易过时；靠模型名猜，又会猜错。

比较稳妥的做法是保守判断：认识的模型才发图，不认识的不发。

```ts
if (/llava|vision|qwen.*(vl|omni)|minicpm-v|pixtral|internvl/.test(model)) return true
if (config.provider === 'anthropic') return /claude-(3|4|5)/.test(model)
if (config.provider === 'openai') return /gpt-(4o|4\.1|5|6)|o[34]/.test(model)
// ...
return false
```

判断不了时，可以让用户选择“总是发送”或“不发送”。默认用“自动”：只有认识的视觉模型才发。

这个默认值很重要。早期把图片发给一个不支持图片的模型，接口直接报错，整章生成失败。现在如果不确定，就只发文字，图片用图注和 alt 兜底，至少不会把主流程打断。

模型能力表会过时。今天支持的模型，明天可能改名；今天不支持的模型，下个月可能更新。比较稳的做法是：内置一份保守列表，同时允许用户覆盖。用户明确知道自己的模型能看图，就切到“总是发送”；不知道，就保持“自动”。

也可以做一次轻量的能力探测：发一张很小的测试图，看接口是否接受。但探测本身也要花钱，而且可能被服务商判定为异常请求。大多数产品用“保守默认 + 用户开关”就够了。

## 二、装饰图先过滤掉

不是所有 `<img>` 都值得发。

可以用一个很朴素的正则：

```ts
const DECORATIVE_IMAGE =
  /logo|icon|二维码|qr\s*code|封面|cover|装饰|divider|spacer|bullet|tracking|pixel/i
```

它匹配 alt 和 caption。命中就不发图，只保留文字说明。

这个规则会误伤一些真的有用、但恰好叫 “cover” 的图。但比起把每本书的封面、出版社 logo、分割线都发给模型，这点误伤可以接受。用户如果真需要，可以切到“总是发送”。

另外，太小的图也不发：宽或高小于 80 像素，或者文件小于 256 字节。它们大概率是图标或占位符，发给模型只是浪费 token。

装饰图过滤只能做粗筛，不能做最终判断。一张名为 `chart-cover.png` 的图可能是封面，也可能真的是图表。比较稳的做法是：命中关键词时默认不发，但在报告里记一笔“跳过了 N 张疑似装饰图”，让用户有机会检查。

图片提取也要注意顺序。按 DOM 出现顺序编号，图注和附近正文跟着同一张图走。不要把所有图先收集起来再排序，否则图注和图可能对不上。

## 三、压缩到模型需要的尺寸

一张书里的扫描图可能有两三千像素宽，几 MB。模型不需要这么高的分辨率，请求体也扛不住。

比较稳的做法是等比缩放到最长边 1,200 像素，先按 JPEG 质量 82 输出；如果还超过 1.5 MB，再降到 68。小于 80 像素的图直接跳过。

```ts
const scale = Math.min(1, MAX_IMAGE_DIMENSION / Math.max(image.width, image.height))
const width = Math.max(1, Math.round(image.width * scale))
const height = Math.max(1, Math.round(image.height * scale))
```

压缩前先铺一层白底。有些 PNG 是透明背景，直接转 JPEG 会变成黑底，图里的文字就看不清了。

还要有总大小限制：单次请求的图片总量不超过 6 MB，最多 8 张。超过的图不发，但保留图注、alt 和附近正文。这样即使模型没看到图，也能从文字里知道“这里有一张关于 X 的图”。

压缩会损失细节。图表里的细小文字、表格里的数字，缩到 1,200 像素后可能看不清。如果内容以文字为主，可以考虑先 OCR 或让用户手动截图；如果以结构为主，压缩的容忍度更高。

多张图之间也要有优先级。正文里第一次出现、靠近当前小节、图注更完整的图，通常比页面底部的装饰图重要。数量超限时，按这个顺序取舍，而不是简单截断前 8 张。

有些图其实不需要视觉模型。纯文字截图可以先 OCR，表格可以解析成文本，公式可以转成 LaTeX。视觉模型更适合“文字描述不了的形状和关系”，比如流程图、架构图、照片。先做一轮分类，能转文字的转文字，能省下不少 token。

## 四、图片也要参与缓存 key

同一章、同一个模型，如果图片换了，读薄结果应该重算；如果只是正文排版变了，图片没变，不应该重算。

所以缓存 key 里除了正文，还要有图片签名：

```ts
imageSignature: args.imageSignature ?? ''
```

签名可以是每张图原始 data URL 的哈希。图片顺序变了、内容变了，签名就变。只改排版或章节标题，不会让整章重新生成。

这个细节看起来很小，但图片很大的章节，重算一次很贵。缓存 key 少考虑一个维度，用户就会为同一张图反复付费。

签名要用原图，而不是压缩后的图。压缩参数以后可能调整，如果签名跟着压缩结果走，改一次参数就会让所有缓存失效。用原图内容做哈希，缓存更稳定。

图片顺序也要进签名。同样的两张图，顺序换了，模型看到的上下文可能不同。签名可以按顺序拼接每张图的哈希，而不是把所有哈希排序后再拼。

## 五、除了图本身，还要告诉模型图在哪

只发一张图，模型不知道它在讲什么。所以每张图最好带三类文字：

- 图注（caption）；
- alt 文本；
- 图片前面最近的正文片段，最多 180 字左右。

拼成一段提示：

```text
[图1] 图注：系统架构；alt：三层架构图；附近正文：请求先经过网关……
```

这样模型能把图和上下文对上。特别是流程图、表格截图，附近正文往往比图注更有信息。

## 六、失败时要有文字兜底

视觉请求失败的原因很多：模型不支持、图片太大、格式不对、服务商超时。不要让这些错误直接打断整章生成。

一个简单的策略是：

- 不确定模型是否支持视觉时，不发图；
- 单张图压缩失败，就跳过这张，保留图注；
- 请求因为图片失败，可以重试一次不带图片的版本；
- 报告里说明这次用了几张图、有没有跳过。

用户不一定需要知道每张图的处理细节，但需要知道“这次生成有没有看图”。如果一张关键图表没发出去，结果的可信度是不一样的。

## 七、图片隐私比文字更敏感

图片里可能有手写笔记、身份证、聊天截图、白板上的内部信息。用户点“生成”时，未必意识到这些图会被上传。

如果产品支持视觉，最好在预检里明确写“本次会发送 N 张图片”，并让用户能预览是哪几张。涉及本地书籍的插图，问题不大；涉及用户自己上传的截图，就需要更谨慎。

缓存也要考虑隐私。图片缓存如果落在磁盘上，要放在用户数据目录里，并且提供清理入口。不要把含有人脸或证件的图片长期留在临时目录。

## 八、怎么测试图片处理

测试图片不止是“能不能识别”。可以准备几类样本：

- 一张正常图表；
- 一张透明背景 PNG；
- 一张超宽长图；
- 一张小于 80 像素的图标；
- 一张几 MB 的高清扫描图；
- 一张名为 `cover.png` 但内容是图表的图；
- 一组超过 8 张的图片。

检查重点不是模型回答得多好，而是流程是否稳定：有没有跳过、有没有压缩、有没有超限、报告里有没有说明。图片处理出错时，应该降级到文字，而不是让整次生成失败。

## 九、模型看到的图，怎么回到笔记里

图片被模型理解之后，结果要能回到用户的阅读场景。

如果笔记里只说“图中展示了三层架构”，用户还是要回去翻原图。更好的做法是保留图片来源：图 id、页码、附近正文。点击引用时，能跳到原图或对应段落。

如果模型根据图片生成了新描述，也要标明“来自图片理解”，不要和原文引用混在一起。图片理解可能有误，用户在引用时需要知道这是模型对图的解释，不是作者原话。

图片数量也要写进生成报告。用户看到“本次使用了 3 张图，跳过 2 张装饰图”，才能判断结果是否覆盖了关键图表。

## 十、上线前可以逐条检查

- 是否判断了模型是否支持视觉？
- 默认策略是否保守，是否允许用户强制开关？
- 是否过滤了 logo、二维码、封面等装饰图？
- 是否跳过了过小的图片？
- 是否压缩到合理尺寸，并处理了透明背景？
- 是否有单张和总大小限制？
- 图片是否参与缓存 key？
- 是否给图片附上了图注、alt 和附近正文？
- 视觉请求失败时是否有文字兜底？
- 报告里是否说明用了多少张图？

视觉功能听起来很“模型能力”，实际做起来大部分是工程问题：怎么找图、怎么过滤、怎么压、发几张、发多大、发失败了怎么办。

图片不是越多越好。先问这张图是否真的承载了文字没说的信息，再决定要不要花那个 token。

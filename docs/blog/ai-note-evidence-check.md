# 让模型引用原文，为什么不能只靠“再问它一遍”

做检索增强、读书笔记或者任何“根据材料回答”的功能，很容易遇到一种情况：模型给出的答案旁边挂着一段“原文引用”，读起来严丝合缝，复制到原文里搜，却搜不到。

句子可能只是被改写了一遍。意思没变，措辞变了，然后它被放进了“原文依据”里。

这不是某个模型特有的毛病。生成任务的目标是“写出一段像答案的话”，不是“从材料里摘一句话”。当格式要求里有一个 `quote` 字段，模型会尽量填一句看起来像引用的内容。它未必在故意编，它只是在完成生成任务。

以下内容来自一个项目实践中的理解过程。项目里做的是读书笔记：模型先读薄一章，再提炼卡片，每张卡片要附原文依据。为了让这个“依据”可信，我试过几种办法，最后留下来的是一个很笨的方案：在本地做字符串核对，找不到就不给“已核对”。

## 一、为什么不能让模型自己检查

最开始的方案很自然：生成完再问模型一句，“你确定这些引用都来自原文吗？”

答案是它很确定。每次都确定。

原因不复杂。模型在生成时已经沿着一个上下文相信那句话是对的，再问一遍，它只是继续沿着同一个语境往下写。让模型判断“这句话是不是原文”，本身也是一次生成，不是检索。

更麻烦的是，这种自检会给人一种虚假的安心感。界面上多了一个“已核对”的标记，用户就不再回去找原文了。可这个标记来自另一个可能犯同样错误的模型。

换一个模型来检查会好一点吗？有时会，但两个模型仍然是在读同一段上下文，做同一种“像不像”的判断。它们可能一起错，而且成本翻倍。只要核对的目标是“这句话是否逐字出现在原文里”，就应该用检索，而不是再生成一次。

所以核对最好放在模型之外。能用确定性代码做的，不要交给概率模型。

## 二、完全匹配之前，先做归一化

原文和模型输出之间，最常见的差异不是内容，而是标点：中文引号、英文引号、省略号、全角空格、换行。直接 `includes` 会把很多真引用判成假引用。

一个简单的归一化函数，把大小写、空白和常见标点都去掉：

```ts
function normalizeForMatch(value: string): string {
  return value
    .toLowerCase()
    .replace(/[\s　]/g, '')
    .replace(/[“”"'‘’「」『』（）()【】\[\]…—–\-·、，,。.；;：:！!？?《》<>]/g, '')
}
```

然后要求整段命中：

```ts
export function verifyQuote(quote: string, chapterText: string): boolean {
  const needle = normalizeForMatch(quote)
  if (needle.length < 6) return false
  const haystack = normalizeForMatch(chapterText)
  return haystack.includes(needle)
}
```

这里有两个看起来很小、其实很关键的决定。

第一，最短长度设为 6 个字。太短的片段，比如“专注”“环境”，在任何章节里都能命中，标成“已核对”没有意义。

第二，要求整段命中，而不是只匹配前 24 个字。我一开始试过截断匹配，后来发现这正是最危险的情况：模型写了一句“前半句真、后半句编”的引用，前半句能在原文找到，后半句是它自己加的。截断匹配会把它判成真引用。

整段匹配会误伤一些合法引用，比如模型在引用中间加了“……”省略。但比起放过假引用，我宁愿多标几个“未核对”。

归一化也有边界。全角/半角、繁简、异体字、数学符号，处理得越多，规则越复杂，也越容易把不同内容抹成一样。比较稳妥的做法是只处理空白和常见标点，其余保持原样。宁可多报“未核对”，不要把两段本来不同的话判成同一段。

如果材料本身有多个版本，比如同一本书的不同译本，核对还要带上版本或章节 id。只在当前章节里搜，能避免把另一章的句子误认成这一章的原文。

## 三、完全匹配失败后，怎么找最接近的句子

有些模型不会直接抄原文，它会轻微改写。完全匹配失败后，可以再做一层“找最接近的整句”。

做法不复杂：把引用和原文都切成二字片段，算重合比例，取分数最高的句子。只有分数超过阈值才返回，否则返回空字符串。

```ts
const score = hits / Math.sqrt(grams.size * Math.max(1, hayGrams.size))
// ...
return bestScore >= 0.72 ? best : ''
```

这里不需要追求一个“正确”的阈值。它取决于你更怕哪一种错误：

- 阈值低：更多引用会被判成“找到了”，假阳性变多；
- 阈值高：更多真引用会被判成“找不到”，假阴性变多。

知识点卡片和原文引用可以用不同的阈值。知识点本身就是概括，不能要求它和原句一样，0.25 左右就能找到语义相关的句子；引用依据要求更高，0.72 才考虑接受。

但不管阈值多少，这层逻辑都只能给出“最接近的候选”，不能证明引用为真。两句话如果共享足够多的二字片段，仍可能被误判成同一句；反过来，作者用了大量同义词改写，也可能找不到。

它的作用不是“证明”，而是“把不确定暴露出来”。

也有人会问，为什么不用编辑距离、embedding 相似度或者专门的 NLI 模型。编辑距离对长文本太慢，而且换一个同义词距离就会很大；embedding 能找到“意思相近”，但引用要的是“字面一致”，语义越相近，越容易把改写当成原文；NLI 模型能判断蕴含关系，却不能告诉你这句话是否逐字存在。

这不是说那些方法没用，而是它们解决的是另一个问题。引用核对的第一层应该是确定性的字符串匹配，后面才轮到语义。顺序反过来，界面上的“已核对”就会变得很廉价。

## 四、界面上要区分“已核对”和“未核对”

生成结果里，每条引用可以带一个 `quoteVerified`。界面只在这个值为真时显示“已核对”。

找不到完全匹配的引用，显示“未核对”；知识点和论点这类本来就不是逐字引用的内容，显示“位置/概述”。演示模式下统一显示“演示样例”，不会出现“已核对”。

这几个标签看起来只是文案，实际上决定了用户会不会把一句话当成作者说的。差一个“已”字，性质就变了。

如果产品里已经有“来源”或“引用”这样的 UI，最好同时提供“查看原文”的入口。用户点一下能看到上下文，比一个孤零零的绿色勾更可靠。

假阳性的代价通常比假阴性高。少标一个“已核对”，用户最多多花几秒钟确认；错标一个“已核对”，用户可能把改写当成作者原话引用出去。所以阈值、文案和颜色都应该偏向保守。未核对不一定是错误，它只是一个“还没有被证明”的状态。

如果核对失败，不要直接把整条卡片删掉。卡片本身可能仍然有价值，只是引用需要人工确认。更好的做法是保留卡片，把引用区域标成“未找到原文”，并提供“查看本章”按钮。

也不要因为核对失败就自动让模型重写一遍。模型可能把句子改得更像原文，但仍然是改写；而且每重写一次都要花钱。核对是给用户看的信号，不是自动修补的触发器。

## 五、引用太长或太短，都不好核对

引用不是越长越可信。太长的引用更容易出现标点差异、省略和换行，匹配失败率更高；太短的引用又容易在任何地方命中。

一个比较实用的范围是 20 到 200 字。超过 200 字，可以拆成几句分别核对，或者只核对最关键的一句。少于 10 字，最好要求模型补充上下文，否则“已核对”没有意义。

引用也不一定非要是一整句。有时候作者的观点跨了两句，模型只引了后半句。这种情况下，可以允许“包含在原文中”的匹配，但要确认引用的起点和终点都在同一段里，不要跨段拼接。

## 六、回查能补什么，不能补什么

读薄稿生成后，还可以做一次“回查”：把原文再发一遍，让模型指出稿子里漏掉了哪些重要信息。回查结果会写进报告，告诉用户“有 N 处可能遗漏”。

但回查本身也是模型生成的。它能提醒“这里可能少了一个限定条件”，不能替我们发现所有错误。所以我只在两个条件同时满足时才做回查：

- 原文至少 2,500 字；
- 读薄稿相对原文的压缩率低于 0.72，也就是确实删掉了不少东西。

如果原文很短，或者几乎没怎么压缩，再花一次请求去回查，收益很小。这个判断很粗糙，但比“每次都用最贵的流程”更接近真实使用。

回查结果也不应该当成硬门槛。它说“漏了三点”，不代表那三点一定重要；它说“没漏”，也不代表稿子就完整。更合理的做法是把回查当成一份提示，和生成报告放在一起，让用户自己判断。

如果回查本身失败了，不要因此让整次生成失败。读薄稿已经生成，可以正常展示，只是在报告里注明“本次未完成回查”。

## 七、这套东西没有解决幻觉

说清楚：逐字核对只能解决“假引用”，解决不了“模型理解错了”。一段真实引用，仍然可能被放在错误的论点上；一张卡片仍然可能把作者的限定条件删掉。

它解决的是另一个问题：不要用界面上的“已核对”去掩盖不确定性。

以前看到一句漂亮的引用，会默认它是原文。现在会先看标签。如果没有“已核对”，就知道这句话需要自己回去找一遍。

这个动作很小，但它把判断权还给了人。

## 八、上线前可以逐条检查

- 引用是否做了标点和空白归一化？
- 是否要求整段命中，而不是只匹配前缀？
- 太短的引用是否被排除？
- 完全匹配失败后，是否有“最接近句子”的兜底？
- 兜底结果是否有明确的置信度阈值？
- UI 是否区分“已核对”“未核对”和“位置/概述”？
- 演示数据是否避免了“已核对”这类误导性标记？
- 回查是否只在成本可接受时触发？

这些问题没有统一答案，但每一项都值得在界面上说清楚。用户不需要知道背后的算法，只需要知道这个勾是怎么来的。
